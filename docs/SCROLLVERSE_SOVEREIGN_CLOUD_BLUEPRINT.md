# ScrollVerse Sovereign Cloud — Platform Blueprint

Status: PROPOSED ARCHITECTURE / ZERO-COST PLANNING PHASE
Working title: ScrollVerse Sovereign Cloud (SV Cloud). The name is provisional; no company, product, service, or deployment is represented as launched.

## 1. Mission

Build a portable, provider-independent application delivery platform that can progressively reproduce the useful capabilities of Vercel, validate those capabilities with real tests, and eventually offer a reliable platform to other builders.

The objective is not to clone Vercel's brand or proprietary internals. It is to build an independently designed platform with comparable developer workflows, transparent operations, stronger portability, explicit security boundaries, and optional self-hosted infrastructure.

Principles:
- Own the control plane and deployment experience.
- Portable execution: OCI containers, standard Git, HTTP, DNS, TLS, and S3-compatible object interfaces.
- Provider adapters: no provider-specific assumptions in core business logic.
- Local-first development: useful engineering progress must continue without paid cloud resources.
- Evidence before claims: distinguish designed, implemented, locally tested, remotely tested, and production-operated capabilities.
- Secure by default: isolated builds, least privilege, encrypted secrets, audit trails, quotas, and fail-closed controls.
- Human authority: agents may analyze and propose; sensitive external actions require explicit authorization.
- No forced migration: existing ScrollVerse services remain unchanged until a reviewed migration plan is approved.

## 2. Reality and scope

A complete Vercel-scale platform is a substantial infrastructure and operations company, not a single web application. It requires compute capacity, storage, networking, security engineering, incident response, billing, support, and ongoing operating capital.

We can begin building the software and validating it locally with existing equipment and open-source components. We cannot truthfully promise a zero-cost global edge network, production-grade isolation, uptime, or Vercel-equivalent service before infrastructure exists and is tested.

The strategic target is reduce single-vendor dependence, not pretend that hardware, internet transit, DNS, registrars, certificate authorities, and physical hosting can be eliminated. Each external dependency should have a documented adapter, fallback, export path, and recovery procedure.

## 4. Reference architecture

### Control plane
Project, team, repository, deployment, environment, domain, secret-reference, and usage APIs. A deployment state machine moves through queued, building, artifact-ready, deploying, and ready / failed / cancelled. A policy engine handles permissions, quotas, environment separation, and approvals. Every privileged change produces an audit event. Provider adapters sit behind stable interfaces.

### Build plane
Git checkout occurs in a disposable workspace. Framework and package manager detection reads repository metadata. Untrusted project code never runs inside the control-plane process. Builds run through BuildKit/buildpacks in constrained workers with CPU, memory, disk, process, time, and network egress limits. Workers produce immutable OCI images and signed build metadata, then destroy workspaces and temporary credentials.

### Runtime plane
Immutable images run as isolated workloads behind an ingress proxy. The platform supports health checks, gradual traffic switching, rollback, and per-project quotas. Preview and production environments remain separate by identity, secrets, networks, and policy.

### Data and observability plane
PostgreSQL stores control-plane metadata. Redis-compatible storage supports queues, locks, and rate limits where appropriate. S3-compatible object storage stores artifacts and logs. OpenTelemetry provides traces, metrics, and logs. Backup is not considered proven until a restore drill succeeds.

### Agent plane
Agent 00 coordinates specialist analysis. Specialists operate through typed, least-privilege tools. Agents can inspect, draft, test, and recommend. Deployment, domain, billing, secret, destructive, and production actions require explicit human approval. Agent outputs carry evidence labels and source references.

## 5. Delivery phases

### Phase 0 — Architecture and local proof (no paid cloud)
1. Freeze this capability map and create a threat model.
2. Inspect existing ScrollVerse repositories and identify reusable components rather than duplicate them.
3. Define provider-neutral interfaces and the deployment state machine.
4. Build a local Compose-based control-plane prototype.
5. Deploy one static sample site and one containerized HTTP app to a local runtime.
6. Generate logs, health checks, local preview URLs, and rollback to a previous image.
7. Run security tests against build isolation and environment boundaries.

Exit evidence: repeatable local deployment from Git to running container; test results; documented restore and rollback.

### Phase 1 — Single-node private alpha
When resources and budget are available, provision a dedicated host. Add durable queues, isolated workers, object storage, TLS ingress, backups, quotas, audit trails, monitoring, alerting, and incident runbooks. Test host, worker, queue, and storage failures and recovery.

Exit evidence: repeatable deploys, verified restore, bounded resource use, documented incident response.

### Phase 2 — Multi-node and developer platform
Add scheduler adapters and worker pools; team/project RBAC; Git provider adapters; build cache; environment promotion; preview comments; custom domain verification; DNS adapters; artifact retention; SBOM/provenance; image signing; vulnerability scanning; metering and transparent usage limits.

### Phase 3 — Public beta
Only after independent security review, capacity tests, abuse controls, privacy/legal review, support processes, and operating budget: invite external developers; publish service limits, status page, terms, privacy notice, incident process, and data export/deletion process; prove tenant isolation; conduct disaster-recovery and penetration testing before general availability.

### Phase 4 — Advanced platform
Framework-aware builds and remote cache; serverless-style functions and scheduled jobs; global edge/CDN integration and regional deployment; managed Postgres/Redis/object storage through pluggable backends; observability dashboards; preview environments; deployment protection; policy automation; optional self-hosted/on-premise control plane.

## 8. Security baseline

- Never run customer build scripts inside the API/control-plane process.
- Never mount the Docker socket into untrusted build containers.
- Use rootless workers and disposable workspaces; stronger sandboxing is a release gate for public multi-tenant builds.
- Default-deny worker network egress; explicitly allow only required package registries and source endpoints.
- Use short-lived, project-scoped Git credentials; never pass long-lived personal access tokens to build jobs.
- Keep control plane, build workers, and tenant workloads on separate trust boundaries.
- Encrypt secrets at rest; decrypt only for the authorized workload; never return secret values to the console.
- Sign artifacts and retain provenance linking source commit, builder, dependencies, and image digest.
- Enforce quotas and request limits before resource allocation.
- Require human approval for production, billing, domain, secret, and destructive changes.
- Test tenant isolation as a first-class security property.

## 9. Cost and dependency policy

The first milestone must be achievable on existing local equipment without paid cloud provisioning. Avoid purchasing domains, servers, managed databases, or subscriptions during the planning/prototype phase.

Before selecting any paid host or external service, prepare a monthly fixed/variable cost estimate; egress, storage, backup, and bandwidth estimates; hardware and hosting failure assumptions; export and migration procedure; provider outage fallback; and owner approval.

Self-hosting reduces platform lock-in but does not remove electricity, connectivity, hardware replacement, transit, domain registration, certificate, or security-maintenance costs.

## 10. First engineering sequence

1. Inventory existing repositories and assets: deploy, build, Git, Vercel, DigitalOcean, storage, and CI components.
2. Write threat model and architecture decision records.
3. Define deployment API contract and state machine.
4. Create local Compose environment with PostgreSQL, Redis, API, worker, and ingress.
5. Implement a no-op/test build worker and deploy one static sample.
6. Add a containerized sample deployment with health checks and rollback.
7. Add contract tests for Git, builder, runtime, and storage adapters.
8. Produce an evidence report with costs, limitations, and next gates.

## 11. Capability evidence labels

- PROPOSED — design only.
- IMPLEMENTED — code exists.
- LOCAL-TESTED — verified on a local machine.
- CI-VERIFIED — automated repository checks passed.
- STAGING-VERIFIED — deployed to isolated staging and runtime tests passed.
- PRODUCTION-VERIFIED — live production behavior observed with evidence.
- BLOCKED — dependency or prerequisite prevents the next gate.

A passing CI job does not prove a running deployment. A local demo does not prove multi-tenant safety. A service is not public-ready until its operations and security gates pass.

## 12. Immediate decision gate

Before implementation beyond the local prototype, inspect existing repositories and select which repository owns the control plane, which components can be reused without breaking Agent 25, which local machine/resources are available, whether local development uses Docker or Podman, and which sample app is safe to deploy first.

No production service is migrated, replaced, or disabled by this blueprint.
